英语作文批改助手 — 优化审查

2026-10-27 · 审查面：src/ 4,169 行 + public/ 4,680 行 + migrations + CLAUDE.md　·　基线 npm run check 通过
最终执行口径（2026-10-27 已落地）：词数采用 200-500 词（不采纳本报告原 P0-1 的 120-150）；图片 token 通用按 1600/张，DeepSeek 模型按官方文档 1024/张。
一句话结论
工程质量明显高于典型个人项目——CSP 走哈希、配额与计费分层、AI 输出净化、游客数据接管都考虑到了， 真正的坑集中在三处方向性错配：评分口径与官方题干不一致；长耗时链路没有对抗基础设施超时，且关键写入不原子； "批改完就结束"没有形成学习闭环。前两类会让真实学生立刻撞墙，第三类决定有没有复购价值。
  • 教学正确性：默认提示词要求 200-500 词，上海卷官方题干是 120-150 词——合规作文会被判"词数严重不足"。
  • 可用性：带题目图的付费批改会因图片 token 估算虚高 50-100 倍被 402 拒绝。
  • 可靠性：结算/计次写在结果落库之前，落库失败 = 钱扣了、次数减了、报告没有。

P0 — 会产生错误结论或直接失败 5 条

P0-1
默认提示词的词数口径写错，且与自家示例数据互相打脸
src/utils/prompts.ts:56src/utils/prompts.ts:172src/utils/prompts.ts:16src/sample/seed.ts:9

现状：SH_GAOKAO_ESSAY_PROMPT 写"词数要求 200-500 词；词数不足或超出过多应扣分"，全文润色也要求"控制在 200-500 词"，GENRES.desc 同样写 200-500。但 seed.ts 的示例作文是 127 词 / 121 词，assessment 写的是"符合 120-150 词要求"，CLAUDE.md 也写 120-150。

后果：上海高考 Guided Writing 官方题干原文是 "Write an English composition in 120-150 words"（2024 真题，多源一致）。一篇完全合规的 130 词作文进来会被判词数不足、扣内容分；修改稿和润色稿会被扩写到 250-300 词，学生照抄等于在考场写超标作文。这不是体验问题，是教错方向，而且同一系统内示例（127 词"符合要求"）与规则（200-500）自相矛盾，学生点开示例再交自己的作文，信任当场崩。

改法：三处统一 120-150（建议 130±15，≤115 或 ≥170 才判词数问题）；word_count_assessment 固定输出"当前词数 / 要求区间 / 差值"；seed.ts 两条文案跟着对齐。仓库里不能再同时存在两个词数区间。
P0-2
图片 token 按 base64 字符数折算，虚高 50-100 倍，带图付费批改直接 402
src/routes/essays.ts:35-37src/routes/essays.ts:467src/routes/ocr.ts:159

现状：estimateImageTokens = images.join('').length / 4。单张 data URL 上限 400,000 字符 → 单张估算 100,000 tokens，三张 300,000。deepseek 档 inputPer1k = 0.4 分，一张图即冻结 ≈40 分，而真实多模态输入通常 1-2k tokens/图。

P0-3
结算与计次都在结果落库之前，落库一失败就是"钱扣了、次数减了、报告没有"
src/routes/essays.ts:516-527src/routes/essays.ts:538-545src/routes/essays.ts:560

现状：顺序是 settle → recordSuccess → INSERT INTO reviews。若 INSERT 抛错（D1 5xx、行超 2MB），外层 catch 因 settled = true 不再 release，返回 502。用户积分实扣、免费次数 -1、库里零记录。

后果：这正是你在计费侧专门规避过的那类问题（"没批改却少了额度"），只是换到了批改侧。而且重试一次会再扣一次。

改法：db.batch([insertReview, insertQuotaEvent])（D1 batch 即事务），顺序反转为先落结果再计次；batch 失败时把已拿到的 result 照常返回给用户（结果是对的，别丢），后台记 error 告警。
P0-4
三处并发写入没有唯一约束兜底：同稿批两次、版本重号、示例灌两份
src/utils/quota.ts:125src/routes/essays.ts:319-322src/routes/essays.ts:138-153

（a）游客门禁是 TOCTOU：checkReviewGate 读"未批改过" → 隔 30-90 秒 AI 调用 → recordSuccess 写行，中间无互斥。quota_events 只有普通索引，双标签页 / 超时重试 / 多 isolate 都能让同一稿批两次、计次 +2。BYOK 车道连 inflight 锁都不占。

（b）版本号 MAX+1：drafts 无 UNIQUE(essay_id, version)，并发写出两个"二稿"；游客 3 稿门禁用的就是预读 version，可写第 4 稿。前端 Tab 按 version 渲染（明确不重排），重号后展示与批改引用全串。

P0-5
"最高 22 分"是刻意设计，但界面按 /25 展示，学生只会以为系统坏了
src/utils/prompts.ts:44src/utils/prompts.ts:113src/utils/validate.ts:52-61

现状：提示词硬性规定"内容≤9、语言≤9、结构≤4，总分≤22，无论多优秀"，sanitizeReview 也用 9/9/4 收敛并强制 finalScore = sum（parsed.score 因此是死代码）。压分纪律本身合理（防 AI 放水），问题在呈现：前端一律 /25，从未告知上限；二稿反馈块还写死了 上一稿得分：x/25，模型看到的基准也跟着失真（19/25 像"还行"，19/22 像"接近封顶"）。

P1 — 用户可感知的失败 / 明显浪费 12 条

P1-1
AI 重试不区分错误类型，最坏 6 分钟，且会超过 Cloudflare 100s 空闲超时
src/utils/ai.ts:10src/routes/essays.ts:491-509src/routes/ocr.ts:185-221

除 429/1015 外任何异常都进第二次 attempt：BYOK key 失效（401）、模型名错（400）、90s 超时都会再打一遍，叠上双端点 failover 与 1015 就地等待 12s，最坏 ≈ 2×90s×2。而 Cloudflare 对客户端连接的空闲超时约 100 秒，超出返回 524（HTML 错误页）——前端 api.js:21 直接 resp.json()，解析 HTML 抛 "Unexpected token <"，用户看到兜底文案而非"超时"。更糟：billing hold 5 分钟过期，超时请求 settle 时 hold 已 expired，charged=0，等于免费白用一次。

改法：只对「JSON 解析失败 / sanitize 校验失败」重试，4xx（非 429）和 abort 立即失败；给 callAI 传 deadline，剩余预算不够一个新端点就不再换端点；单次超时降到 40s，总预算硬顶 90s。
P1-2
30-90 秒的同步请求，既不能取消也不能恢复

P1-5

分数趋势 + 三条必改		 S/M 现有导出是完整报告（长、密），但学生真正要给老师看的是"比上次好在哪、还有哪三条没解决"。复用 export.js 的 docx 管道做一页 A4 摘要，成本很低，场景很实（家长会、周记）。

看起来该做、其实先别做

想法不做的理由
班级 / 多人协作有了第二个人就要处理权限、共享、教师端、通知一整套，D1 + Workers 的单租户形态也撑不住多租户演进。现在最大价值是"一个人的私教"，去做第二件事会把第一件做浅。
多题型一起上GENRES 扩展位留得好，但每个题型都要独立评分锚点、独立 validate 区间（9/9/4 现在还是硬编码）、独立调优。先让上海大作文做到"学生信这个分数"，再谈第二个。
流式输出批改结果是结构化 JSON，流式只是把"等 60 秒"变成"看字符爬"，对信任帮助很小，反而增加解析复杂度。该解决的是 P1-2 的"可中断可恢复"，不是流式。
语音 / 口语评分与"作文批改"的用户心智不在一处，另需音频链路与评分标准，纯属稀释。

如果只能改 3 件事

  • 1. 修词数口径（P0-1）——半小时的活，但它决定这个工具是在教学生写对还是写错。任何 UX 打磨，在有系统性错误的评分面前都无意义。
  • 2. 批改原子化 + 唯一约束（P0-3 + P0-4）——一个 db.batch 加两条唯一索引，约 40 行，直接消灭"扣钱没报告""同稿批两次""版本重号"三类最伤信任的问题，也是后面所有幂等改造的地基。
  • 3. 批改 job 化（P1-2 + P1-1）——一次投入同时解决 524 超时、刷新失忆、无法取消，是所有交互体验的地基。
只做一件的话选 1；只做两件的话选 1 + 3（学生能真正用下去优先于后台绝对正确）。
审查方法：三个并行通道（后端健壮性 / 前端 UX / 产品与教学价值）各自通读源码，结论逐条回到代码人工核对，重复项合并； 行号对应 2026-10-27 仓库状态。词数口径已用 2024 上海高考真题题干原文交叉验证（"in 120-150 words"）。 基线检查 npm run check（tsc --noEmit + CSP 哈希）当前通过。
